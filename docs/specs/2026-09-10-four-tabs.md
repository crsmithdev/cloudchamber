# Four tabs: browse, ideate, check, write

The UI holds one list and one reading pane per stage. Today three tabs cover
four stages: `develop` carries both the check gate and the drafting gate, and
`ideate` shows a brief it has no use for. This spec splits them.

Decided with Chris on 2026-09-10, from the mockups in `tmp/mockups/`. The
mockups are the visual record; this file is the rule set.

## The tabs

| Tab | Holds | Reading pane |
|---|---|---|
| browse | the corpus | unchanged |
| ideate | every draw, for ever | seed, distribution, examples. No brief |
| check | every draw with a brief, or building one | the brief, the findings, gate 1 |
| write | every draw with a schedule | the schedule, the scenes, the screens, gate 2 |

## Rules

1. A draw stays in ideate after a candidate is chosen. The gate is the only
   place to develop a second candidate, so the gate must stay reachable. A
   draw therefore appears in ideate and in check at the same time.

2. Check lists briefs flat. A fork is a separate draw, so one batch can put
   several rows in check. Each row names the candidate it came from, `#2 ·
   0.42`, which is the fact that tells two rows of one batch apart.

3. A draw enters check when a candidate is chosen, not when the brief is
   written. The premise and the vignette exist at that moment. The outline,
   the two context vignettes and the ending land one at a time. The row shows
   the stages as they complete and the pane shows each part as it arrives.
   The pane reads artifacts, not the files under `briefs/`, because the files
   are written last and all at once. Gate 1 stays inert until the brief exists.

4. A passed draw goes by its verdict kind. `cloudchamber gate <draw> pass` at gate
   1 records a verdict of kind `brief`; at gate 2 it records kind `draft`. The
   kind names the tab: `brief` keeps the draw in check, `draft` moves it to
   write. No column records this; the verdict log already does.

5. One function, `tabFor(draw)`, decides the tab, and the lists and the router
   both use it. The routes are `#check/<id>` and `#write/<id>`. `#develop/<id>`
   resolves through the same function, so an old link lands where the draw is.

6. A brief in check names the draw and candidate it came from and links back
   to ideate. A repair and a fork put hops in the chain, so the helper walks
   `repaired_from` and `forked_from` back to the draw that ran the premises.

7. The rail shows no counts.
