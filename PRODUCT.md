## Platform

web

## Users

One operator: the author of the pipeline. He knows every stage, but he reads
the UI after long detached runs, and on 2026-09-16 he marked many of its terms
as confusing. Labels therefore use plain words: a step is a verb and a noun, a
state says what he does next ("review findings"), and a tooltip says what a
control or a step does. Internal names such as gate 1 stay in the code.

Other writers may get access later. This is not confirmed and no second user
has ever run the tool. Future work keeps labels and empty states honest enough
for a second reader, but does not build onboarding, accounts or roles.

## Product Purpose

Cloud Chamber turns a seed into a checked story brief, then into a draft.

A seed and six example passages become five premises. Each premise is executed
as a 400-word vignette. The operator chooses one at the gate. The draw then
derives an outline, two context vignettes, an ending and a brief. The brief is
checked, repaired and passed at gate 1. Drafting derives a schedule, writes
the scenes, screens them and stops at gate 2. A kept draft exports
`drafts/<draw>/story.md`.

Success is a brief the operator keeps, reached without hand-writing the
ideation.

## Positioning

The premises are asked for as a stated probability distribution, and the draw
samples a named band of it: `tail` 0 to 0.1, `off-centre` 0.1 to 0.35,
`standard` 0.35 to 1. The tail is the default, so the pipeline is built to
return the strangest defensible reading of a seed rather than the strongest
conventional one.

Three other mechanisms carry the same intent:

- A verdict log. Every accept, reject and flag on a passage or theme is
  recorded and replayed, so a regeneration does not lose earlier judgement.
- Lore settings as five lists — bodies, events, instruments, places, terms.
  Each stage of a draw under a setting loads the lists it needs, each list
  whole. Caps: 40 entries a list, 45 words an entry.
- A pinned ledger. The brief's settled facts are extracted once per repair
  chain and every later round is measured against that same ledger.

## Operating Context

The operator runs this alone on one machine, under WSL2. The UI is served
locally.

Work is long and detached. A full draw to a kept story takes about 36 minutes
and 79 model calls. Theme extraction runs about one story a minute. The
operator starts work, leaves it, and comes back.

The CLI, the HTTP API and a Claude Code skill drive the same actions as the UI.
`docs/knobs.md` is generated by `cloudchamber help --md` and is never edited by
hand. The files in `docs/specs/` are the design of record.

Three of the four tabs hold a running operation and a judgement surface at the
same time:

| Tab | Monitors | Judges |
|---|---|---|
| browse | nothing | the corpus: keep, pass, flag |
| ideate | a draw running the premises | the gate: which premise to develop |
| check | check and repair rounds | findings, then gate 1 |
| write | schedule, scenes, screens | flags, then gate 2 |

Browse is the only pure judgement surface. Extraction happens outside the UI.

## Capabilities and Constraints

Four tabs, fixed: browse, ideate, check, write. `tabFor(draw)` decides where a
draw appears, and the lists and the router both use it.

Red-teaming is not a coming stage. The six checkers — `derivation`, `ledger`,
`structure`, `resemblance`, `claims-extract`, `claims-verify` — plus the repair
rounds and gate 1 are the red team, and they shipped as the check tab.

There is no separate story stage. The write tab produces the story.

A draw stays in ideate after a candidate is chosen, because the gate is the
only place to develop a second candidate. A fork is a separate draw.

Open decisions, not to be invented:

- What `reject`, `delete` and `archive` each mean on a draw. The operator
  raised this on 2026-09-09 and it is unresolved.
- Whether "assembly", the last unclaimed stage in the ideation spec, ever
  becomes a surface here.

## Brand Commitments

The name is Cloud Chamber. It was renamed from Fog Belt; the tool renamed, the
writing project did not.

The voice is terse and factual throughout: short labels, no marketing register,
no exclamation.

## Evidence on Hand

Real content exists and mockups must use it:

- `data/cloudchamber.db`, the live store. It is not in git.
- The brief directories under `briefs/`.
- Exported drafts go to `drafts/<draw>/`.
- Real store fixtures extracted for mockups: `tmp/mockups/draws.json`,
  `gate.json`, `checked.json`, `findings.json`, `brief.json`, rendered to
  static HTML by `tmp/mockups/gen.ts`. These are local scratch and not in
  git; only `worlds.ts` and the two stylesheets are tracked.
- Ten hand-written reference stories in `stories/`. These are setting-a
  reference material, not pipeline output.
- The evaluation protocol in `docs/evaluation.md`, and its recorded runs in
  `evals/`.

Absences future work must not fill with invention: the write tab has rendered
real content once. No second user has ever used the tool, so there is no usage
data, no testimonial and no adoption number.

## Product Principles

1. The operator's judgement is the product. The pipeline proposes; he keeps,
   passes and flags. Every surface exists to make that judgement fast.
2. Record the verdict, never re-ask it. Work already judged is not judged
   again, and a regeneration inherits what was decided.
3. Long work runs detached. The operator is often away, so state has to be
   readable on return without replaying a log.
4. Density earns its place. He reads twenty rows at once on purpose; a surface
   that shows three facts where twenty fit is a regression.
5. Say what happened, including the cost. Steps, model per stage, call counts
   and durations are part of the interface, not debug output.

## Accessibility & Inclusion

No product-specific standard has been established. The tool has one operator,
on one machine, with no stated access need. Future work meets ordinary web
baselines — keyboard reachability, focus visibility, contrast — but no
requirement beyond that was set.
